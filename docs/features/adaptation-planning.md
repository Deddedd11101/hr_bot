## Повторный тест без удаления истории

Admin-only `GET /app/employees/{employee_id}/adaptation-retest` показывает preview
плана и активных адаптационных progress; POST с fingerprint и same-origin Origin
создаёт SQLite backup/quick_check и применяет под BEGIN IMMEDIATE. Drift,
посторонний диалог или item starting/in_progress блокируют сброс.
Текущие items получают status=archived и отдельный history entry_key; original
entry_key/status/время архива сохраняются в calculation_json.retest_archive.
Они исключаются из текущего preview, но не удаляются; plan API возвращает
archived_items. Ссылки на них и started/completed dates остаются прежними.
Выбранные progress закрываются с причиной прерывания, pending confirmation
очищается, связанные in_progress answer runs помечаются interrupted. Ответы,
файлы, Telegram identity и история доставок не удаляются; completion events
не генерируются. Pending requests только этих adaptation flows гасятся без отправки.
Новый план создаётся отдельно пользователем; reset не назначает даты и не шлёт
сообщения. Старые archived items продолжают защищать flows от generic auto jobs.

# План адаптации

## Даты и шаблон

Общий шаблон задаёт порядок этапов, scenario_key, группу PM/не-PM/все, anchor, смещение в рабочих/календарных днях и время. У каждого этапа стабильный key: два Пульса одного сценария имеют разные записи и очереди. Шаблон сохраняется с revision compare-and-swap, циклы запрещены. GET ничего не записывает. Изменение шаблона не переписывает индивидуальное расписание; удалённые/скрытые этапы с историей остаются видны.

Начальный порядок из файла «запуск сценариев.xlsx»: организация, первый день (+0), первая неделя (+5 рабочих), тест PM-1 (+9 рабочих), Пульс-1 (+5 рабочих от планового теста), середина (+45 календарных), тест PM-2 (-14 календарных от конца), Пульс-2 (+5 рабочих от планового теста), окончание по группе (-3 рабочих от конца). Не-PM используют те же расчётные тестовые якоря без показа тестов. Даты не зависят от фактического завершения предыдущего этапа.

Пустая середина считается как first_workday +45 календарных дней; пустой конец — +3 календарных месяца, не 90 дней, с ограничением числа последним днём целевого месяца. Заполненные даты карточки приоритетны, в том числе исторически автоматически сохранённые: происхождение старых значений неизвестно, они не переписываются. Новый перевод кандидата в адаптацию заполняет пустые midpoint/end по этим правилам. GET preview возвращает adaptation_midpoint, adaptation_end и adaptation_end_source=saved/calculated/missing; в карточке пустые поля показывают автоматические подсказки, без записи результата GET в Employee. Явная середина используется этапом middle.

Первый день при создании/изменении карточки должен быть рабочим по активному производственному календарю. Неизменённая историческая дата не блокирует несвязанные правки. Authenticated working-days API возвращает разрешённые даты; DatePicker блокирует остальные. Отсутствующий год/дата — явная ошибка, не fallback на субботу/воскресенье. Производственный календарь влияет на итоговые даты этапов: нерабочий результат переносится вперёд. Сам конец остаётся календарной датой. Старт 10:00 Europe/Moscow, совпадения разводятся по порядку на 10 минут. Role_scope/employee_scope не расширяются по названиям групп.

## Создание и интерфейс

До первой записи этапа видна одна кнопка «Запланировать адаптацию», без пустого списка. Свежий GET открывает окно с датами всех ещё не созданных этапов, без чекбоксов. Старые завершённые прохождения включаются повторно с предупреждением. Ошибка обязательного этапа блокирует создание всего плана. full_plan=true проверяет состав на backend; прежний частичный API сохранён для совместимости. «Обновить расчёт» сбрасывает неподтверждённые даты и ничего не записывает.

Подтверждение отправляет fingerprint и rules_confirmed=true. POST атомарно создаёт EmployeeAdaptationPlanItem и FlowLaunchRequest launch_type=adaptation_plan. Повторный POST/дубли/stale fingerprint дают 409, неверные/прошедшие/нерабочие даты не принимаются. Чужая pending очередь того же сценария блокирует создание; два независимых Пульса плана допустимы. Fingerprint включает даты, midpoint, должность, blocked status, шаблон, строки плана и версии календарей. Технические timestamps — UTC, времена очереди — naive local TIMEZONE.

После создания — компактный список с датами, статусами и меню действий. Completed этапы свёрнуты; прогресс считает только их, не старый ScenarioProgress. Повторяющиеся названия имеют порядковый суффикс. PATCH даты использует expected_at; разрешены planned/blocked/failed/cancelled, но не уже обрабатываемые/идущие/завершённые. Отмена требует подтверждения, удаляет pending request и сохраняет историю. Failed/cancelled можно повторно запланировать только явно. Ошибка не закрывает модалку и не объявляется успехом.

«Порядок и правила» под шестерёнкой сохраняют полный редактор общего шаблона. Сопровождение/документы и разовые запуски/история свёрнуты, но остаются доступны; ОС, файлы, sidebar не удалены. Статусы обновляются раз в 15 секунд только при выбранной вкладке карточки «Адаптация» и видимой странице браузера. При возврате на вкладку, фокуса или видимости выполняется немедленное обновление. Первичная загрузка плана остаётся однократной при монтировании карточки. Polling приостановлен в диалогах/во время записи и не затирает draft. Кнопка «Обновить статусы» удалена; автообновление не меняет расписание.

## Массовый перенос

Изменение первого дня само не двигает очередь. «Пересчитать оставшиеся» получает свежий preview, показывает старые и новые даты (включая ранее изменённые вручную) и требует подтверждения. POST replan меняет только planned/blocked с существующим pending request. Сохраняются ids этапов/очередей, completed/starting/in_progress/interrupted/failed/cancelled не переносятся и не восстанавливаются. Ошибка любого этапа откатывает весь пакет. Состав, fingerprint, ограничения сценария и календарь проверяются под блокировкой; начавшийся запуск даёт 409. При переносе сохраняется актуальный calculation snapshot. Удалённые из шаблона этапы с ошибкой нужно разобрать отдельно, массовый перенос не угадывает их судьбу.

## Доставка и история

Пары сотрудник/сценарий с индивидуальным планом не получают legacy automatic root jobs; зарегистрированные jobs игнорируются и при исполнении, включая отменённые этапы с историей. Явные ручные запуски и internal follow-up не отключаются. Manager-assignment trigger не дублирует сценарий плана.

Worker проверяет реального recipient, включая руководителя, и не перезаписывает waiting progress: запуск остаётся blocked/pending. Перед отправкой request atomically claimed, этап starting. После аварии между claim/отправкой автоматического повтора нет; требуется диагностика. In_progress означает старт движка, не прочтение. Завершение меняет только связанный этап; новый Пульс не стирает прошлую историю. 10 минут между стартами не гарантируют освобождения диалога.

Reset linkage отменяет будущие этапы subject, активные context/recipient помечает interrupted, completed сохраняет. Delete удаляет индивидуальный план subject. Логика XLSX, ОС, документов и context/recipient ownership не меняется. UI, очередь и HTTP 200 не доказывают доставку Telegram; новая доставка и пользовательская приёмка отмечаются отдельно.
