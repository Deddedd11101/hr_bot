## Сбор коллег: детали и сопоставление матрице

Если задан `GRADE_REVIEW_WEBAPP_URL`, новые сборы получают приглашение с кнопкой
«Открыть опрос» вместо запуска диалога сценария. Все критерии и открытые вопросы
загружаются разом. Участник может изменить любой ответ до подтверждения отправки.
Отправка завершает участие и включает ответы в расчёт среднего. После неё
ответы доступны только для просмотра, независимо от фиксации итога HR.
Черновики на сервере не сохраняются. Сборы в чате остаются в прежнем режиме.
Опрос не даёт доступ к личному кабинету.

Новый сбор фиксирует навыки, веса, требования грейдов и до20 открытых вопросов
в snapshot_json. Шаблон по умолчанию предлагается из профиля сотрудника;
HR может выбрать другой активный шаблон до создания сбора. Изменение справочника
не меняет уже созданный опрос. После skill-этапов идут text/survey_answer вопросы.
Ответы остаются привязаны к respondent и question key, не включаются в средние.
Существующие сборы без open_questions продолжают работать.

Среднее по навыку пересчитывается при чтении из завершённых ответов коллег,
без округления исходных баллов и без превращения пропусков в нули. Незавершённые
анкеты не включаются. До явной фиксации HR это предварительный итог. При фиксации
сохраняется immutable снимок индивидуальных scores/comments, среднее и метод
агрегации; исправление решения HR не меняет исходные ответы коллег.

Рекомендация — объяснимое сопоставление с frozen expectations, а не автоназначение:
самый высокий активный на момент создания шаблона грейд, все требования которого
покрыты средними баллами. Нужен хотя бы один ненулевой критерий. Неоценённый
ненулевой критерий либо отсутствующее требование исключает полное соответствие.
Покрытие = sum(min(mean, required) * weight) / sum(required * weight) * 100;
явно нулевые требования не увеличивают знаменатель. Показываются unmet,
unassessed и missing_requirements. Отсутствие полностью покрытого уровня не
подменяется Junior. Порог большинства/автоматическое повышение не применяются.

HR может явно выбрать current_grade_id и comment при фиксации; только это
подтверждённое решение записывается в профиль. Legacy finalize без payload
сохраняет прежний контракт. Повторный finalize с другим грейдом отклоняется:
для изменения используется существующий correction с историей версий.

Вкладка разделена на «Оценки» и «Цикл развития». Сбор показывает итог и список
отвечающих с переключением графика; подробная оценка содержит навыки и текстовые
ответы. Финальная запись хранит копию этих деталей. При сравнении сразу выбраны
две последние final-записи; легенды содержат даты/ID и различают сплошную/пунктир.
Сравниваются только совместимые навыки по существующему frozen-history контракту.


Черновик можно сохранить в архив через `POST /api/grade-assessments/{assessment_id}/archive`.
Это immutable снимок со статусом `archived`, а не завершённое ревью; `finalized_at`
не заполняется. Он сохраняется в истории только для чтения и не участвует в
сравнении final-оценок. Архивирование освобождает единственный активный черновик.
Повторное архивирование идемпотентно; final нельзя архивировать, archived нельзя
изменять или завершать. Физического удаления оценок нет.

# Грейды и история оценок

## Цикл развития

Явный запуск из плана адаптации и этап ИПР могут использовать один сценарий
в разные даты. Назначение в Grade (даже на паузе) не запрещает adaptation_plan
request. Для одного сценария более ранний due request адаптации получает
приоритет перед этапом Grade; будущий request и старая история не резервируют
этап навсегда. Занятый получатель ждёт освобождения диалога, не требует отмены
другого корректного запуска. Общие автоматические triggers по-прежнему
подавляются владельцем плана; правила массовых/обычных ручных запусков
этим изменением не расширяются. Неопределённая доставка автоматически не повторяется.

В каждом этапе разрешены 0..10 независимых действий: сценарий сотруднику,
опрос ОС о сотруднике выбранным коллегам, сбор оценок навыков по выбранному
шаблону. На этапе через 6 месяцев новые сборы оценок 360 не добавляются.
Сохранённые ранее остаются в текущем плане, но не переносятся в следующий цикл.
Список пуст — только напоминания HR/руководителю. Выбор всех трёх
сценариев больше не обязателен для нового редактора. Legacy PUT сохранён
для старых циклов; после перехода на список действий он отклоняется с 409,
чтобы старый клиент не затёр новые настройки.

Даты/пауза/revision относятся к этапу, claim/ошибки — к каждому действию.
Коллеги, занятые другим диалогом, остаются в очереди, остальные получают
опрос независимо. Неизвестный результат отправки не повторяется автоматически.
При новом завершённом ревью уже настроенный цикл переносит список действий
предыдущего цикла; настройки не назначаются сотрудникам автоматически.

«Рассчитать по производственному календарю» подставляет будущие даты 6/12
месяцев в форму, с переносом нерабочего дня вперёд. Пользователь может изменить
предложенные даты вручную до сохранения. Кнопка не перепланирует запущенные
этапы. Без загруженного календаря расчёт сообщает, какого года не хватает.
У отдельного действия можно указать своё время не раньше даты этапа. Без
переопределения используется дата этапа. Планировщик ждёт выбранную дату и
не повторяет уже запущенные действия при переносе соседних. Абсолютные даты
действий не копируются при открытии следующего цикла.
Одноимённый «Пульс опрос» из каталога опросов не выбирается в цикле: используется
сценарий с получателем «Сам сотрудник», без списка отвечающих. Старое неверное
назначение требует исправления; при наступлении срока опрос не уйдёт коллегам.

## Оценки коллег

Во вкладке «Грейд» можно запустить сбор отдельно или включить его в этап цикла.
Шаблон/навыки/важности замораживаются при запуске; каждый выбранный сотрудник
получает Telegram-опрос с баллами 0..4 и «Не могу оценить». Ответы принадлежат
respondent, результаты — карточке subject. Самооценка остаётся отдельным HR-ревью.
Внутренние шаблоны `scenario_kind=grade_review` не входят в редактируемый каталог
сценариев/опросов и не подменяют последний Excel ОС или тег `{ос}`.

Приветствие берётся из `assessment_intro` специализации. В новых сборах
`[ИМЯ]` подставляет имя оцениваемого из карточки. Стандартное приветствие
первоначального импорта заменяется при создании сбора; собственные тексты
специализаций и уже созданные шаги не переписываются. Вопросы по навыкам
генерируются по замороженным названиям и критериям уровней; без критериев
используется общая шкала 0–4. Обычный редактор сценариев эти тексты не меняет.

Новый сбор после последнего ответа показывает отвечающему только его черновик:
таблицу навыков, баллов и открытых ответов. Используется `sendRichMessage`,
при явном отказе Bot API применяется текстовая версия. Кнопка «Утвердить»
публикует ответы для HR и учитывает их в среднем; «Оценить заново» удаляет
только неподтверждённые ответы этого коллеги и открывает первый шаг того же
сбора. Кнопки прежней сводки не меняют новый черновик. Ранее созданные
шаблоны и завершённые оценки не мигрируются.

В пилоте `GRADE_WIDGET_REVIEWER_IDS` один личный Telegram Widget на попытку
показывает закрытые вопросы с прогрессом и постраничную итоговую таблицу.
Состояние и кнопки обновляются на том же сообщении. Ответ выбирается обычными
кнопками под виджетом; открытые ответы вводятся в чате и сохраняются, но не
дублируются в итоговой таблице виджета. Для навыков с рубрикой имя сотрудника
показывается рядом с прогрессом, а под названием навыка остаются только критерии.
Для навыков со шкалой 1–4 виджет запрашивает недостающие части критериев у бота,
и начинает предзагрузку дополнительных страниц следующего навыка заранее.
При переходе текущая карточка остаётся видимой, пока все критерии новой не готовы.
Выбор, пропуск и «Назад» доступны внутри карточки. У новых интерактивных вопросов
нижняя клавиатура не отправляется; при загрузке виден индикатор внутри виджета.
У ранее отправленных виджетов сохраняется совместимое поведение клавиатуры.
При явном отказе API используется прежний
формат. При неоднозначной сетевой ошибке повтора нет.
Пустой список отключает пилот для новых сообщений без изменений БД.

HR видит отдельные паутинки и предварительное среднее только завершённых
опросов. Итог фиксируется явно после ответа всех выбранных коллег и при наличии
хотя бы одного оценённого навыка. По каждому навыку считается арифметическое
среднее известных баллов; пропуски не нули. Категории затем усредняются с весами
1/1.5/2 по навыкам. Дробные баллы не округляются до целых, final сохраняется
в обычной истории с frozen catalog и ссылкой на запуск сбора. Повторная
финализация не создаёт дубль. Кадровый грейд автоматически не повышается.
У зафиксированного среднего можно исправить кадровый грейд с аудитом; сами
средние не редактируются вручную, иначе перестанут соответствовать ответам.
Для отдельного мнения HR сохраняется обычное новое ревью.

API/история хранят исходную шкалу 0..4. На паутинках и сводке категорий
показывается `среднее / 4 × 100%`: 3 = 75%, максимум 100%.
Это не процент выполнения требований Senior/Lead. Старые snapshots не переписываются.

Вкладка «Грейд» содержит отдельный блок цикла: ближайший запуск, остаток дней,
этапы, историю прошлых циклов и статусы напоминаний. HR явно выбирает сценарии
проверки ИПР через 6/12 календарных месяцев и новой оценки через 12 месяцев.
До настройки существующие оценки не создают отправок. Для импортированных
оценок без исходной даты нужна явная дата оценивания, не дата импорта.

Шаблоны ИПР, предназначенные только для этого цикла, задаются с запуском
«Только вручную» (`manual_only`). Цикл запускает их по датам своих этапов,
независимо от общего trigger шаблона. Это исключает независимый запуск
от середины/конца адаптации у сотрудника без настроенного цикла. Само
назначение «ИПР» не отключает общий trigger: менять его нужно явно.

Месяцы календарные, отсутствующий день конца месяца ограничивается последним
днём целевого месяца. По умолчанию время 10:00 МСК; годовая новая оценка идёт
после второго ИПР с интервалом 10 минут. Переноса по производственному календарю
для этого цикла нет. Даты ещё не начатых этапов можно менять; просроченную
активацию сервер запрещает, чтобы не отправить сразу старые задания.

При явном сохранении старого цикла уже запущенные legacy-этапы переносятся
в список действий с прежним статусом, без повторной отправки. Их состав
не меняется; будущие этапы можно редактировать независимо. Простое открытие
карточки существующую конфигурацию не мигрирует.

Напоминания HR и назначенному руководителю учитываются отдельно от запуска.
Используются проверенные numeric Telegram identity; неизвестный адресат или
ошибка доставки видны как ошибка, не как успех. Занятый диалог блокирует запуск
до освобождения. Claim фиксируется до внешнего I/O: при неопределённом результате
после сбоя автоматического повтора нет, HR должен проверить доставку.

Пауза запрещает новые claims, но не отменяет уже начатую отправку. Конкурирующие
изменения настроек защищены revision. Завершение новой оценки обновляет только
уже настроенный цикл; старые этапы сохраняются в истории. Исправление баллов
не меняет дату отсчёта. Решение о кадровом грейде всегда остаётся за человеком.

## Исправления завершённого ревью

Команда «Исправить оценку» для final historical-ревью допускает дооценку навыков
по замороженной матрице и optional `current_grade_id` (в том числе null).
Можно исправить только грейд с пустым values. Для последнего final обновляется
текущий кадровый профиль и добавляется решение; исправление старого final не
меняет профиль. Специализация/исходная дата/сроки ИПР не меняются. Обычные
PATCH/finalize и архив не открывают final для произвольной записи. Нужны причина,
UUID и edit_token; stale/изменённый replay — 409. Предыдущий snapshot сохраняется.

Прежний JSON целиком сохраняется в `grade_assessment_revisions` вместе с actor_id, причиной и временем. Значения и актуальный snapshot обновляются одной транзакцией, график/сравнение читают актуальную редакцию. `created_at`/`finalized_at`, provenance, матрица и исходный комментарий сохраняются; `updated_at` заполняется сервером после правки и показывается как «Последнее изменение» в МСК. В UI доступны предыдущие версии только для чтения; правка — не новое плановое ревью. Историю правок удаляет только существующая явная admin purge-команда вместе с удаляемой оценкой после verified backup. Выкладка подтверждена в [[stage-change-log]]; пользовательская приёмка реального сохранения остаётся открытой.

## Первичный импорт и необязательный грейд

Кадровый грейд необязателен при preview/save и создании draft: `current_grade_id=null` не мешает оценить навыки, сохранить final и сравнить оценки. Специализация обязательна. Значение грейда не выводится из баллов.

Admin-only первичный XLSX импорт доступен в импорте каталога. Предпросмотр ничего не пишет: показывает все матрицы и персональные колонки, карточку, число фактических/пропущенных баллов и причину пропуска. Листы вопросов не импортируются. Сопоставление — точное нормализованное имя либо уникальная пара фамилия/имя в начале ФИО; сокращённые имена задаются явно в JSON `aliases`, без автоматического fuzzy matching. `zero_sheets` явно разрешает пустые требования как 0 только для перечисленных листов.

Применение сверяет fingerprint файла, каталога, имён и истории оценок под SQLite write lock. Неоднозначные/отсутствующие карточки, повтор сотрудника и неизвестный грейд блокируют пакет. Любая существующая история сотрудника означает пропуск (включая draft/архив): импорт её не заменяет и не финализирует. До первой записи создаётся verified SQLite backup; все шаблоны/новые final-оценки сохраняются одной транзакцией. Повторный импорт не создаёт дубли. Шаблоны объединяются штатным catalog importer с отдельными требованиями каждой специализации; старые frozen snapshots остаются неизменными.

Сохраняются числовые баллы 0–4, отсутствующие не превращаются в 0. Грейд берётся только из файла либо остаётся null. В final добавляется `import_source` (digest, лист, колонка, `original_review_date=null`), комментарий явно отличает неизвестную дату исходного ревью от даты импорта. Чужие карточки не создаются. После выкладки runtime с nullable грейдом откат к старой версии требует отдельной проверки: старый код не умеет создавать/редактировать такие оценки.

XLSX parser принимает матрицы как с отдельной строкой кадровых грейдов, так и без неё: первый навык во второй строке не пропускается. `н/д`, `n/a`, `нет данных` и `—` в персональных баллах означают отсутствие оценки, а не ноль. Непустые данные за лимитом 1000 строк/100 столбцов отклоняются, пустые форматированные строки допускаются. Эта подготовка parser сама по себе не импортирует персональные оценки в карточки.

## Оценка и решение

Обычный UI — обзор последней оценки (паутинка), история и кнопка новой оценки.
Без оценок показывается «Ранее не оценивался». Форма объединяет шаблон,
кадровый грейд, комментарий и навыки; «Сохранить оценку» атомарно сохраняет
решение, баллы и final-снимок, без отдельной финализации. Отмена новой формы
ничего не пишет. Existing draft открывается для продолжения с замороженным
шаблоном. request_id UUID защищает повтор HTTP-запроса от дубля final/решения;
matrix_version защищает от незаметной смены шаблона. Нет автоматически угаданного
повышения: грейд явно выбирается человеком в той же форме.

При двух final выбор двух ревью под графиком автоматически включает сравнение.
На паутинке только общий набор сопоставимых оценённых навыков, с одинаковыми
весами из прошлой матрицы для обоих рядов. Несопоставимые навыки видны отдельно
в свёрнутой детализации. Архив свёрнут; его действие независимо от сравнения.

Администратор может необратимо удалить все прочие оценки выбранного сотрудника,
оставив одну активную. Это отдельное подтверждаемое действие в «Управлении
историей», не обычное архивирование. Сервер сверяет expected_ids под write lock,
создаёт SQLite backup с quick_check, только затем удаляет строго связанные values
и assessments. Без резервной копии или при изменившейся истории операция запрещена.
Резервная копия хранится в backups рядом с SQLite, не доступна через web. Профиль,
история кадровых решений и оценки других людей не удаляются.

Грейд сотрудника назначается отдельным решением оператора, не результатом формулы. В UI нет выбора целевого грейда или прогнозируемых баллов. Первая оценка фиксирует фактические компетенции; последующее ревью создаётся заново, без копирования прошлых баллов. Повышение не обязательно: можно сохранить прежний грейд с комментарием в истории решений.

EmployeeGradeProfile сохраняет текущие специализацию/грейд. Смена этих полей и непустой комментарий записывают append-only employee_grade_decisions с actor_id, датой, предыдущим/новым грейдом и снимками подписей. GET не создаёт профиль/историю. История до появления этой таблицы не выдумывается. Старые target_grade_id/target_specialization_id и final snapshots физически не удаляются; legacy view/API расчётов остаются совместимыми. Новые оценки не наследуют цель, UI сохранения профиля очищает прежнюю цель явно.

## Снимки и неизвестные значения

Один draft на employee защищён SQLite partial unique index. Создание фиксирует каталог в catalog_snapshot.draft_catalog: состав навыков, критерии, категории, revision, важность, требования/подписи грейдов и специализацию. Идентификатор версии матрицы — SHA-256 содержимого. Правки каталога после начала не меняют этот draft. Старые drafts без такого wrapper читаются по legacy contract; их final snapshots не переписываются.

Финализация блокируется при несохранённых UI-изменениях, требует подтверждения и замораживает view-model. Final PATCH запрещён; повторная финализация идемпотентна. После final API не читает живой каталог для пересчёта истории. snapshot_version=2 дополнительно хранит review_mode, scale_version, matrix_version, assessed. Техническая created_at — время создания записи, не доказанная дата исторического ревью. Импорт без исходной даты показывается как «дата не указана», не оформляется задним числом автоматически.

Уровни факта — целые 0..4: Нет, Понимание, Умение, Экспертиза, Лидерство. Пустое значение/н/д не равно нулю: assessed=false, не включается в средние. Явный 0 остаётся оценкой. PATCH level=null удаляет значение нового draft, возвращая его в неоценённое состояние. Категории без оценок не рисуются нулевыми на графике. Важность 1/2/3 имеет вес 1/1.5/2; категории считаются только по известным фактам. Legacy goal progress/gaps сохранены только для старых снимков/совместимости, не являются частью нового процесса.

## Сравнение

Authenticated GET compare принимает две final оценки одного сотрудника. Другой employee_id — 404; draft/невалидный snapshot не сравниваются. Выбор двух завершённых ревью даёт график пар фактических баллов по компетенциям, не прогноз. Общий средний разных матриц не используется для вывода о росте.

Сопоставление — по постоянному skill id и одинаковой semantic revision, категории и scale_version. Новая компетенция — added, исчезнувшая — removed; изменение смысла/шкалы — changed без delta; отсутствие оценки — unassessed. Legacy snapshots без revision сравниваются консервативно по сохранённым определениям, неизвестный legacy 0 не считается подтверждённой оценкой. При редактуре названия оператор может явно выбрать editorial, сохранив revision; default semantic повышает revision при изменении имени/критериев. Смена категории/complexity повышает revision независимо от editorial. Система не определяет смысл изменения автоматически и не объединяет похожие имена.

## Каталог и импорт

/app/grades использует дизайн-систему HRBot: матрица, грейды, специализации, категории, навыки, импорт. Справочники архивируются через active=false. Стандартные Junior/Middle/Senior/Lead создаются только при пустом каталоге. Назначение HRBot employee остаётся единственным источником identity, отдельная таблица людей из Grade не импортируется.

JSON импорт — dryRun preview, затем expectedFingerprint того же файла/текущего каталога. Применение без актуального preview запрещено и транзакционно. Preview перечисляет добавленные/совпавшие/изменённые компетенции, прежние названия, изменения требований/важности и отсутствующие ids. При id в JSON связывает по id; иначе только точное имя внутри точной категории. Переименование без id считается новой компетенцией; похожесть не используется. Поля change_kind=semantic/editorial и description описывают решение оператора о критериях. Неизвестные поля/шкалы отклоняются. Требования level 0..4, importance 1..3 или ordinary/key/critical; aliases none/нет для 0.

После применения specialization.skill_ids_json задаёт точный состав новой матрицы. Отсутствующие в файле глобальные навыки и старые оценки не удаляются; другие специализации не лишаются навыков. Исторический NULL skill_ids_json оставляет прежний глобальный состав до явного импорта. Экспорт выбранной специализации в JSON сохраняет ids, чтобы следующая редакция могла надёжно различать переименование и новую компетенцию. Ожидания по грейдам — требования матрицы, не личный прогноз повышения.

POST workbook-preview читает только выбранный лист XLSX формата Skills: Категория, Навык, Junior, Middle, Senior, Lead, Важность, далее именованные колонки сотрудников. Ограничения 5 MB/50 MB распакованного XML, максимум 1000 строк/100 колонок; формулы не исполняются и требуют reviewed values. Вопросы опросов не импортируются. Числовые значения сотрудников отделены от текстовых вспомогательных колонок «Столбец …»; н/д — null. Пустые требования отклоняются без явного blank_requirements_zero=true. Excel preview возвращает catalog и assessment_candidates раздельно; UI импортирует только шаблон, не привязывает личные оценки по имени молча.

Первый разобранный источник Skills.xlsx, лист «Системный аналитик»: 5 категорий/45 компетенций. Пользователь подтвердил числовую колонку H и пять пустых Junior-требований как 0. Шаблон без персональных оценок: tools/data/grade-system-analyst-catalog.json. Подготовленные оценки Антона хранятся вне Git и остаются локальным черновиком без подтверждённой даты; другие сотрудники и опросы не импортируются.

## Хранение и проверка

### Поведенческие критерии (06.11.2026)

- Критерии принадлежат паре специализация/навык, а не глобальному описанию навыка: одинаковое название у PM, дизайнера и аналитика не означает одинаковую формулировку. Хранение — nullable `GradeSpecialization.assessment_guidance_json`; SQLite compatibility добавляет колонку без backfill старых оценок.
- JSON import принимает `specialization.assessment_intro` (до2500 символов), `specialization.open_questions` (до20 вопросов по2000 символов) и `skills[].rubric = {levels: {"1": "...", "2": "...", "3": "...", "4": "..."}, na: "..."}` (каждый текст1..600 символов). Preview показывает `rubric_changed`; apply требует прежний fingerprint. Пропуск rubric сохраняет существующие критерии включённого навыка. Экспорт JSON включает критерии, intro и открытые вопросы.
- Новые коллегиальные сборы фиксируют критерии в snapshot. В Telegram каждый навык содержит четыре описания поведения и кнопки1..4/«Не могу оценить»; NA не равен0 и исключается из среднего. Legacy-сборы без rubric сохраняют шкалу0..4. Intro отправляется перед первым навыком. Три открытых вопроса из шаблона подставляются в форму, HR может изменить/удалить их; явно переданный пустой список означает отсутствие вопросов.
- В ручной оценке, её исправлении и детализации общей/индивидуальной оценки доступны раскрываемые «Критерии уровней» из сохранённого snapshot. Старые записи не обогащаются текущими критериями задним числом. При сравнении изменение rubric означает changed без delta, даже если skill id тот же. Формула среднего и решение HR о грейде не меняются.
- Подготовленный пакет `tools/data/grade-rubrics-20261106.json`: 156 навыков (PM23, сервисы24, концепты24, BA43, SA42), source SHA256 и пять отдельных catalog payloads внутри packages. Конвертер `tools/prepare_grade_rubrics.py` читает заголовки, а не фиксированные позиции колонок. Q36 у SA отсутствует в источнике; номера не используются как skill id. Никакие персональные оценки не читаются/не импортируются из исходного Skills workbook.
- В старой SA-матрице три навыка повторяются в корпоративной и soft-категориях; финальный вопросник содержит каждый один раз. Конвертер сохраняет первое вхождение при одинаковых grade-требованиях, иначе отклоняет неоднозначный источник. Live import сохраняет корпоративные skill IDs19/21/22, исключая soft-дубли27/29/31 только из SA scope. Whitespace-only варианты имён сопоставлены с ID через скачанный live JSON, без fuzzy matching.
- Для существующих навыков сохраняются категории и grade-требования исходной матрицы Skills; важность и поведенческие описания берутся из финального файла. Для пяти новых навыков сервисного дизайнера требования1/2/3/4 соответствуют явно подписанным Junior/Middle/Senior/Lead колонкам источника. Удалённые пять навыков исключаются только из состава этой специализации, глобальные записи/история не удаляются.
- Перенос на stage: сначала код/колонка, затем backup и dryRun каждого `packages[].catalog` через существующий `/api/grades/import` с явно проверенным targetSpecializationId. Проверить missing_ids и пять замен у дизайнера сервисов; apply по свежему fingerprint. Не выбирать create-specialization по похожему имени и не менять уже начатые сборы. Этот commit не выполняет live import.

Новая таблица решений создаётся metadata.create_all; nullable skill_ids_json/description и revision default 1 добавляются compatibility patching без переписывания final JSON. Delete employee с final assessment по-прежнему 409; без final удаляются его drafts/values/profile/decision records. Нет публичных employee-grade endpoints, все операции требуют admin-session любой текущей роли. Write routes используют SQLite BEGIN IMMEDIATE; draft writes дополнительно conditional lock против финализации.

Проверки: grade calculations/goals legacy contracts, services/API, compare revisions/ownership, frozen draft/final, missing vs zero, stale import guard, XLSX parsing. Deploy, реальный импорт персональных оценок и пользовательская приёмка фиксируются отдельно. Изменения этого пакета не затрагивают Telegram/scenario runtime.
