# Задачи первого выпуска

Продуктовый scope согласован в PR #11. Здесь описана будущая реализация, не текущий runtime. Статусы задач ведутся только в [[backlog]]. Автоматическое и ручное удаление персональных данных, срок 12 месяцев, очистка файлов/backups и обезличивание статистики в пакет не входят.

## Обязательный контракт запрета доступа

Запрет заблокированного человека должен сохраняться независимо от карточки попытки и активной Telegram-привязки. До освобождения привязки backend обеспечивает сохранение запрета для известного numeric Telegram ID; архивирование, восстановление, reset/disconnect и смена username не снимают его. /start проверяет запрет до создания или привязки карточки. Новая ссылка подключения тоже не должна обходить запрет. Снятие запрета является отдельным авторизованным действием с аудитом, не побочным эффектом восстановления.

Незаблокированному человеку после архива разрешён новый /start без предварительного разрешения HR. Он получает новую попытку с этапом «Не указан»; повторный /start не создаёт ещё одну. Новый Telegram-аккаунт того же человека автоматически узнавать не обещаем. Для заблокированных записей без известного numeric ID нельзя обещать устойчивое распознавание: в BE-01 согласовать обработку таких записей и явно показать ограничение оператору, не связывая чужих людей по username.

## HRB-ARCH-BE-01: модель и общий контракт

**Исполнитель:** backend. **Зависимости:** согласованный scope PR #11; актуальный integration contract identity/linking и lifecycle доставок. PR #10/#12 учитывать, если они вошли в integration, не заменять HR settings linking механизмом кандидатского архива.

**Результат:** проект схемы, матрица доступа и согласованный API/payload для архива, восстановления, запрета, связи попыток и назначений. Имена endpoints/полей определить здесь; frontend не придумывает параллельный контракт.

Критерии приёмки:

- Определены дата/причина/автор архива и восстановления, прежний этап, связь попыток и аудит без удаления старой истории.
- Запрет хранится независимо от активной привязки; определён перенос существующих блокировок без окна, позволяющего обойти запрет, включая записи без numeric ID.
- Определены права просмотра архива/файлов, восстановления, связи попыток и снятия запрета; неясные продуктовые полномочия согласованы с владельцем продукта.
- Описаны успешные ответы, ошибки доступа/конфликта, повторные запросы и занятая Telegram-привязка; утверждены достаточные основания ручной связи попыток.
- DB/Storage review подтверждает схему и compatibility patching через models/schema guard; миграция не удаляет карточки, файлы или историю. Согласованный контракт отражён в docs.

## HRB-ARCH-BE-02: архив, отмена доставок и восстановление

**Исполнитель:** backend. **Зависимость:** BE-01, включая DB/Storage review.

Критерии приёмки:

- HR архивирует отказного кандидата или уволенного сотрудника с причиной; карточка исключается из активных выборок, новых запусков и отправок. Документы, заметки, назначения и история сохраняются.
- Освобождение привязки сохраняет отдельный запрет. Незавершённые процессы отменяются с причиной и аудитом, не удаляются и не отмечаются успешными.
- Проверки охватывают context и recipient, scheduler, manual/mass sends, follow-up, ожидающие ответы и старые callbacks. Для уже захваченной отправки есть повторная проверка; уже переданный Telegram запрос не считается гарантированно отозванным.
- Восстановление возвращает ту же карточку и прежний этап. Доставки, привязка и уже заменённые назначения не возобновляются автоматически; запрет не снимается.
- Если появилась новая попытка или привязка занята, backend сообщает конфликт без слияния/перехвата. Повторные и конкурентные вызовы не дублируют события и не обходят архив.
- Автотесты проверяют сохранность истории/файлов, отмену всех каналов доставки, гонки archive/send и восстановление с конфликтом.

## HRB-ARCH-BE-03: повторный вход, история и назначения для замены

**Исполнитель:** backend. **Зависимости:** BE-01 и BE-02.

Критерии приёмки:

- Незаблокированный новый вход создаёт ровно одну новую кандидатскую попытку; старые статусы, ответы и файлы в неё автоматически не копируются. Архив исключён из active identity matching.
- Запрещённый numeric ID не создаёт и не привязывает карточку после архива/reset/disconnect/восстановления или смены username. Явное снятие запрета авторизовано и журналируется; штатные конфликты identity по-прежнему обрабатываются без угадывания.
- HR может подтвердить и исправить связь попыток с аудитом; история и файлы доступны только по разрешённым правам, не выдаются через бот по совпадению username.
- Payload возвращает назначения для замены с сотрудником, ролью manager/mentor_adaptation/mentor_ipr и архивированным ответственным. После замены или разрешения проблемы список актуализируется; завершённая история назначений не меняется.
- Автотесты покрывают повторный/параллельный /start, сохранение запрета, чужой username, доступ к прошлой попытке и обновление списка назначений.

## HRB-ARCH-FE-01: архив и восстановление в интерфейсе

**Исполнитель:** frontend. **Зависимости:** BE-01 для начала разработки по согласованному payload; BE-02 и BE-03 для проверки на реальном API и приёмки.

Критерии приёмки:

- Есть активный список и архив, причина/дата завершения, история попыток и переход к разрешённым документам/заметкам.
- Архивирование и восстановление имеют подтверждение, поле причины по контракту и состояния loading/error/success; повторное нажатие во время запроса исключено.
- Восстановление не обещает автоматического запуска сценариев или Telegram-подключения. Конфликт с новой попыткой/занятой привязкой отображается с сохранением обеих карточек.
- Состояние отдельного запрета видно независимо от архива и подключения. Действие снятия запрета отделено от восстановления и доступно только разрешённой роли.
- В архиве и затронутых карточках видны назначения для замены с ролью и переходом к сотруднику; после замены данные обновляются без возврата прежнего ответственного.
- Проверены empty/error/forbidden/conflict состояния и соответствие read-only полей API. Использованы текущие shared UI patterns, сборка проходит; пользовательское тестирование остаётся отложенным.

## HRB-ARCH-QA-01: техническая приёмка общего пакета

**Исполнитель:** интегратор с backend/frontend. **Зависимости:** BE-02, BE-03, FE-01; DB/Storage и Docs review.

- На общей integration-ветке проверена цепочка: архив → отмена → повторный вход → связь истории; отдельно блокировка → архив → попытка обхода → отказ → авторизованное снятие запрета.
- Проверены ошибочный архив → восстановление, занятая привязка, новый /start одновременно с архивом, поздняя отправка и назначения всех трёх ролей.
- Обязательные проверки backend по AGENTS: compileall, ruff F821, релевантные smoke/identity/scenario и новые regression tests; frontend build; `python tools/check_docs_contracts.py` и diff check.
- Live docs обновлены по фактической реализации: API, data model, identity/lifecycle/scenario behavior и web surface; текущая готовность отражена в project_state/backlog. Незавершённый пользовательский smoke отмечен явно.
- В пакете нет задачи или механизма автоматического удаления. Деплой выполняет только интегратор отдельным согласованным шагом.

Порядок: BE-01 → BE-02 → BE-03; FE-01 можно разрабатывать после фиксации контракта BE-01, но завершать только вместе с backend. Затем общий QA-01. Новые независимые агенты работают в отдельных чистых feature-worktree от согласованного integration/dependency ref.
