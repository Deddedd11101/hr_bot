# Дневная заметка - 2026-06-15

- Диагностирован stage-инцидент Telegram worker: service оставался `active` и получал updates, но ответы падали с `TelegramNetworkError: Request timeout error`.
- Inbound handlers создавали новый `Bot`/aiohttp session для каждого ответа и оставляли session незакрытой при исключении.
- Runtime исправлен на reuse общего polling `Bot`.
- Добавлена единая настройка `TELEGRAM_PROXY_URL` для Telegram-клиентов web и worker, потому что прямой IPv4-доступ stage к `api.telegram.org:443` timeout-ится, а IPv6 route на сервере отсутствует.
- Stage runbook расширен проверкой реального `/start` round-trip, свежих worker logs и IPv4/IPv6 маршрута к Telegram API.
- Stage восстановлен через RedShield WireGuard selective route: только `149.154.166.110/32` идет через интерфейс `redshield`, SSH, web и остальной трафик остаются на обычном маршруте.
- `wg-quick@redshield`, `hr-bot-web` и `hr-bot-worker` активны и включены в автозапуск; web/worker зависят от WireGuard unit через systemd drop-ins.
- Web и worker выровнены на один Telegram bot token; effective bot проверен через Telegram API как `@ze_hr_bot`.
- Финальная проверка: Telegram API отвечает через VPN, внешний web возвращает auth redirect, свежих `TelegramNetworkError`/timeout в worker logs нет.
- После восстановления сети `/start` для `@AVstrkv` выявил отдельный data-integrity дефект: Telegram user id оставался в `employee_messenger_accounts` за уже удаленной карточкой `id=1`, из-за чего привязка существующей карточки `id=7` падала с `EmployeeIdentityConflictError`.
- Перед repair сделан backup stage DB; осиротевшая messenger account удалена, Telegram identity привязана к существующей карточке `id=7`, контрольный `handle_start_command` успешно отправил ответ.
- В runtime identity helper добавлена защита: конфликтующая messenger account автоматически освобождается только если связанного employee действительно больше нет; конфликт с живой карточкой остается ошибкой.
