# Шпаргалка демо-дня

Это личный сценарий показа, а не документ для демонстрации как roadmap. Если показывать экран с планами, лучше открывать [[roadmap-2026-05-12]].

## Порядок показа

1. Коротко объяснить направление: “переходим к React-first админке, classic оставляем как fallback”.
2. Показать общий экран сотрудников/кандидатов: один пункт `Сотрудники`, переключение внутри страницы.
3. Показать сценарии: workspace, шаги, ветки, детали шага.
4. Показать опросы: тот же workspace в режиме survey.
5. Показать массовые действия: аудитория, preview получателей, подтверждение immediate actions.
6. Показать настройки: HR settings, menu sets/buttons, accounts.
7. Показать [[roadmap-2026-05-12]] как отдельный блок “что дальше”.

## Короткий talk track

“За последние дни мы не просто добавляли экраны, а приводили систему к управляемой архитектуре: документация стала source of truth, React admin стал основным направлением, а classic UI оставлен как rollback. Уже перенесены settings, bulk actions и surveys, сценарии и опросы теперь используют общий workspace. Ближайший фокус — стабилизация, performance и сценарная автоматизация. После закрытия текущего блока переходим к отпускам как новому бизнес-модулю, а затем используем отпуска и self-service сценарии как базу для Telegram Mini Apps.”

## Что важно проговорить

- Старый UI не удаляем резко: он остается fallback, пока React-поверхности проходят parity/smoke.
- Массовые действия стали безопаснее: immediate send/launch требует preview и явного подтверждения.
- Сотрудники и кандидаты теперь не две разные CRM-сущности в навигации, а общий операторский экран.
- Опросы не делались отдельным редактором: они переиспользуют общий scenario workspace.
- Перед отпусками нужно закрыть текущую стабилизацию, иначе новый бизнес-модуль ляжет на неустойчивый foundation.
- Для двух ИП нужно отдельно решить legal/data boundary: вероятнее всего, два раздельных хранилища/БД и явное отображение текущего ИП в UI.

## Если спросят про сроки

| Горизонт | Что сказать |
| --- | --- |
| 1-3 дня | Дочищаем визуальные баги, smoke текущих React pages, проверяем stage. |
| 1 неделя | Performance сценариев, статусные триггеры, часть сценарных correctness gaps. |
| 2 неделя | Scenario transitions, уведомления, LLD по разделению данных двух ИП. |
| 3-5 неделя | MVP отпусков. |
| 6-10 неделя | Telegram Mini Apps foundation + первый production-ready flow. |

## Не обещать без уточнения

- Не обещать “полностью удалим classic UI” до parity-smoke и rollback-плана.
- Не обещать Mini Apps до решения identity/auth/API boundaries.
- Не обещать “просто добавим поле ИП”: требование раздельного хранения может потребовать две БД, отдельные backup/runbook и UI context.
- Не обещать юридическую формулировку без подтверждения. Технически фиксируем требование как business/legal constraint, но финальное решение должен подтвердить юрист/ответственный за данные.
