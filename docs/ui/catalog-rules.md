# Правила каталога дизайн-системы

Каталог живёт на `/app/design-system`. Требования к нему заданы в `docs/features/ui-design-guidelines.md`, раздел «`/app/design-system` как live baseline»: четыре уровня — Foundations, Primitives, Patterns, Review rules — и поимённый список примитивов, которые обязаны быть представлены.

Этот документ не переопределяет требования, а описывает механику: как каталог устроен технически и как его проверять.

Источник правды — реестр `frontend/src/design-system/registry.ts`: из него строятся навигация, порядок, связи и проверки. Отдельных ручных списков компонентов быть не должно.

## Запись описывает ровно один компонент

**Это не новое правило, а невыполненное существующее.** Основной документ перечисляет примитивы поимённо — Button, Input, Textarea, Select, Checkbox, Switch, Badge, Card, Table, Breadcrumb, Tabs, Dialog, Dropdown, Tooltip, Progress, Avatar, Skeleton — то есть требует записи на компонент.

Фактически часть записей собрана свалками: `form-primitives` содержит девять компонентов, `feedback-and-utilities` — шесть, `data-primitives` — пять, `navigation-primitives` — два. Сослаться на `Input` и проверить его в отрыве в таком виде невозможно.

Список из основного документа и есть цель разделения: он снимает вопрос, на какие записи разбивать свалки.

Уровни каталога не смешиваются. Продуктовый уровень (готовые модули и journeys) не заведён — известный пробел, отмеченный в шапке реестра.

## Образцы: две оси — матрица, одна — список

Ряд элементов без подписей не является документацией: видно, что они разные, но нельзя сказать, какой из них какой.

- **`SpecimenMatrix`** — когда осей две. Кнопки: варианты по строкам, размеры по колонкам, обе подписаны. Сравнение идёт и по горизонтали, и по вертикали.
- **`SpecimenList`** — когда ось одна. Подпись слева, образец справа.
- **`Specimen`** — одиночный образец с подписью рядом.

Подпись совпадает с именем варианта в коде: по ней образец и опознают. Реализация — `frontend/src/design-system/specimen.tsx`.

**Числовые значения в подписях берутся из кода, а не по памяти.** Подпись «высота не ниже 32px» уже один раз оказалась неверной: у `xs` — 24px, у `sm` — 28px. Если значение указано, оно должно быть проверяемым.

## Плейграунд

Плейграунд доказывает работу элемента, а не служит скриншотом. Состав — `frontend/src/design-system/playground.tsx`:

- табы вариантов, у каждого своя сцена, поясняющая строка и свой исходник;
- переключатель «Вид / Код»;
- сброс к исходному состоянию.

Внутрь не помещаются сетевые запросы, продакшн-данные и необратимые операции. Только локальные детерминированные фикстуры — **и не имена живых коллег**.

## Грамматика страницы

Порядок блоков одинаков для всех записей, автор не может его переставить:

1. контекст — группа и раздел
2. имя записи
3. назначение
4. статус компонента и путь к исходнику
5. плейграунд
6. обязательные состояния
7. связанные записи

## Статус компонента

Каталог документирует весь кит, но не делает вид, что всё в нём работает. Поле `status`: `product`, `showcase`, `internal`, `unused`, `not-a-component`.

Статус **проверяется машиной**: `frontend/scripts/check-registry.mjs` считает фактическое использование по импортам и требует совпадения с заявленным. Реестр не может утверждать, что компонент в продукте, если его никто не импортирует.

Запуск: `cd frontend && npm run check:registry`. Возвращает 1 при проблеме — годится для CI.

## Что проверяет валидатор реестра

`validateRegistry()` в `registry.ts`:

- уникальность `id` и `href`, совпадение `href` с `id`;
- раздел объявлен и принадлежит своей группе;
- уникальность порядка внутри пары группа + раздел;
- все `related` существуют, нет ссылок на себя и дубликатов;
- покрытие обязательных состояний по семейству, с учётом объявленных исключений.

Валидатор на первом же запуске нашёл две ошибки в самом реестре. Проверка, которая никогда не срабатывает, бесполезна: при изменении правил стоит убедиться, что она по-прежнему падает на заведомо неверных данных.
