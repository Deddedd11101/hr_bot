# Контракт интерфейса — дополнения

Основной контракт уже существует и не дублируется здесь:

| Что | Где канон |
| --- | --- |
| Палитра, тема, жёсткие правила, что запрещено | `docs/features/ui-design-guidelines.md` |
| Token policy, primitive policy, формы, обратная связь | `docs/features/shadcn-component-contract.md` |
| Обязательные состояния по семействам | `REQUIRED_STATES_BY_FAMILY` в `frontend/src/design-system/registry.ts` |
| Живой каталог ролей цвета | `/app/design-system#palette` |

Ниже — только то, чего в них нет.

## Расхождения контракта с реальностью

Контракт формулирует норму, но не отслеживает, соблюдается ли она. Ниже — места, где они разошлись. Список проверяемый: каждое утверждение сверено с кодом.

| Норма | Что на самом деле |
| --- | --- |
| «Toasts use shadcn Base `sonner`» | `sonner` не импортируется ни одним экраном продукта. Обратная связь после действий сделана локальными `message`-состояниями, по-разному на каждом экране |
| Палитра — locked baseline | Светлая тема приведена к порогу: `--primary` = `oklch(0.548 0.116 156.9)`, белый текст даёт 4.62:1. Расхождение осталось только в legacy-слое — `.btn-primary` на `--shell-accent` тёмной темы (`#4aad7a`) даёт 2.78:1. Класс встречается лишь в `index.html` и `scenario_edit.html`, ни один React-экран его не использует. Не чинится, пока не решена судьба legacy-редактора. Расчёт — в `ui/ux-review-rubric.md` |
| Semantic tokens only | Соблюдается в `frontend/src`, но `app/static/react_shell.css` держит 17 собственных `--shell-*` теми же цветами в hex, вне сборки Vite |

## Пробелы кита

Не норма и не нарушение — то, чего в компонентах просто нет. На это нельзя молча полагаться:

| Пробел | Следствие |
| --- | --- |
| У `Button` нет состояния ожидания | Защита от повторного нажатия при сохранении и рассылке ложится на вызывающий код |
| `data-filled` не используется ни одним полем | Заполненное и пустое поле визуально неразличимы |
| Навигационное семейство кита не используется в продукте | Навигация собрана вручную в шелле и в шаблонах Jinja |

## Раскладка внутри страницы

Полоса заголовка приведена к одному виду раньше; здесь — то, что ниже неё. Правила заданы компонентами, а не договорённостью: `PageFilters`, `PageRow` и `PageSection` в `frontend/src/components/ui/`.

**Шапка у страницы одна.** Список называет в ней раздел и показывает счётчик записей, деталь показывает хлебную крошку «Опросы / Название опроса»: раздел кликабелен и уводит в каталог, имя записи остаётся заголовком. Отдельной кнопки возврата «К списку…» нет. Обе полосы — `PageHeader` и `PageDetailHeader` из `frontend/src/components/ui/page-header.tsx`, у них общая геометрия и общий разделитель во всю ширину поля контента. Вторая шапка появляется незаметно: деталь сценария начиналась полосой «Сценарии», а под ней шла карточка с именем сценария — два заголовка подряд, из которых верхний ничего не сообщал об открытой записи.

**Порядок сверху вниз фиксирован:** полоса заголовка → полоса фильтров → содержимое. Между ними ничего не вставляется. Форма создания записи фильтром не является и разворачивается под полосой.

**Текста на фоне страницы не бывает.** Всё содержимое лежит в блоках: полосе фильтров, полосе модулей, карточке. Подпись, лежащая прямо на фоне, не принадлежит ни одному блоку и обычно пересказывает то, что уже написано на модулях — так на дашборде под заголовком висело «Ближайшие события, документы и записи, которые требуют внимания», дублируя имена трёх модулей ниже.

Правило не про любой текст, а про прозаический блок: список, форма и полоса фильтров под него не подходят, в них есть ссылки, кнопки или поля. Проверка так и устроена — ищет прямого ребёнка колонки контента, у которого есть текст и нет ни одного управления.

**Полоса фильтров — не карточка.** Карточка ради фильтров даёт ощущение карточки в карточке, когда ниже начинаются карточки записей. Порядок слотов задаёт компонент, автор его не выбирает: `scope` → `search` (растягивается) → `controls` → `view` (прижат вправо). Все контролы полосы — 32px в высоту.

**Одна поверхность на уровень.**

| Случай | Рамку несёт | Записи внутри |
| --- | --- | --- |
| Страница-список | карточки записей | внешней обёртки нет |
| Модуль с заголовком | модуль | разделяются линиями, без своих рамок и заливок |

Третий уровень вложенности запрещён. До этой работы карточка в карточке была на восьми экранах из девяти, а в `bulk-actions` и `bot-menu` доходила до трёх уровней.

**Грамматика модуля.** Шапка — одна строка постоянной высоты: имя модуля, приглушённый счётчик рядом с ним и одно компактное действие справа. Счётчик начинается с единицы: ноль не показывается ни в модуле, ни в полосе заголовка страницы — пустоту видно по содержимому, а ноль рядом с именем читается как поломка данных. Описания под заголовком нет и слота под него тоже: оно ломало полосу — шапка с описанием оказывалась на 44px выше соседней, и содержимое модуля начиналось настолько же ниже. На 26 модулей продукта приходилось шесть описаний, слот стоил дороже, чем приносил.

Имя модуля — `h2`, а не `div`: это заголовок раздела страницы, и дерево доступности обязано это показывать. У `CardTitle` из кита тег не переопределяется, поэтому заголовок собран в `PageSection` со слотом и классами кита.

Тело — один из закрытых вариантов, автор выбирает форму, а не изобретает её:

| Слот | Что это |
| --- | --- |
| `PageSectionRows` | список записей, разделённых линиями |
| `PageSectionGrid` | сетка равных плиток внутри модуля |
| `PageSectionEmpty` | пустое состояние, одно на весь проект вместо пяти |
| `FieldGroup` из `components/ui/field.tsx` | форма полей |
| просто содержимое | текст, `Alert`, что угодно |

Состояний у модуля два: содержимое и пустота. Загрузка и ошибка остаются на уровне страницы. Пустота центрируется по доступной высоте — модуль вытягивается до высоты соседа по полосе, и сообщение встаёт в середину, а не липнет к заголовку.

**На полосе все доли равны.** `PageRow` принимает количество долей, а не шаблон колонок: дробей, `col-span` и `minmax(...px, ...)` в страничной сетке не бывает. Модуль, которому мало доли, занимает собственную полосу целиком, а не полторы. Лестница брейкпоинтов записана в компоненте один раз:

| Долей | <768 | 768–1023 | 1024–1279 | ≥1280 |
| --- | --- | --- | --- | --- |
| 2 | 1 | 2 | 2 | 2 |
| 3 | 1 | 1 | 3 | 3 |
| 4 | 1 | 2 | 2 | 4 |

Каждый шаг — целое деление полосы, поэтому сирот на переносе не бывает.

**Скелет повторяет реальную раскладку** — тем же `PageRow` и тем же числом долей. На дашборде скелет рисовал четыре колонки там, где контент рисовал две, и страница на ширинах 768–1279px перекладывалась при загрузке.

**Шаг между полосами один** — `--admin-page-gap`, задан прямо в `.admin-page-stack`. Раньше это были `gap-5` в обычном состоянии, `gap-4` в состоянии ошибки той же страницы, `gap-0` в каталоге и жёсткие `18px` в `.react-page`.

**Что переведено.** Дашборд и список сотрудников. Остальные экраны — `documents`, `settings`, `bot-menu`, `bulk-actions`, `scenario-workspace`, `employee-detail` — пока живут по-старому; на них карточка в карточке остаётся.

**Чем проверяется.** Набор `frontend/scripts/ui-checks/suites/page-layout.js`: равенство долей полосы, одинаковая высота шапок модулей полосы, отсутствие текста на фоне страницы, отсутствие вложенных карточек, место полосы фильтров и выравнивание имени страницы по содержимому. У каждой проверки объявлен отрицательный контроль.

Проверки, которым на конкретной странице нечего мерить, отмечаются знаком ⚠, а не провалом: полос модулей нет в списке сотрудников, полосы фильтров нет на дашборде. Провал там, где конструкции просто нет, топит настоящие находки среди ложных.

Витрина каталога кладёт карточки внутрь карточек намеренно — сцена показывает те самые компоненты, о которых рассказывает. Такая вложенность объявлена признаком `data-showcase` и проверкой не считается.

## Наведение на элемент коллекции

У карточек в сетке наведение обозначается **рамкой**, а не заливкой. Основной контракт (`docs/features/ui-design-guidelines.md`) говорит про «мягкое изменение surface» — для одиночного элемента это верно, но заливка целой карточки в плотной сетке читается как выбор, а не как наведение.

Кликабельность карточки обещается тремя признаками сразу: курсор-указатель, рамка и увеличение на 1%. Одной рамки мало — она же используется просто для наведения на некликабельный блок, — а одного курсора не видно, пока не поведёшь мышью. Открывает запись растянутая ссылка внутри `RecordCard`, а не `role="button"` на всей карточке: так точка табуляции одна, фокус подсвечивает карточку целиком, и вложенные чекбокс с кнопками остаются достижимыми.

Действия записи скрыты до наведения и проявляются по нему же и по фокусу внутри карточки. На устройствах без наведения — `@media (hover: none)` — они видны всегда: иначе единственный способ открыть запись оказался бы недостижим на планшете. То же самое для клавиатуры обеспечивает `group-focus-within`, и это проверяется набором.

## Всплывающие слои

Слой, висящий над страницей, отделяется тенью и рамкой одновременно: тень задаёт отрыв, рамка — край. Возвышение берётся из `--shadow-overlay` (`frontend/src/index.css`), в тёмной теме значение плотнее — тень той же силы там смешивается с фоном и пропадает.

Цвета фона для отделения недостаточно: `--popover` равен `--card` в обеих темах, и выпадающий список давал к фону страницы **1.03:1**.

`Tooltip` в это правило не входит — он отделён инверсией фона и стрелкой.

**Ловушка, из-за которой всё это понадобилось.** В `index.css` есть правило:

```css
@layer utilities { [class*="shadow"] { box-shadow: none !important; } }
```

Селектор матчит атрибут `class` целиком, а не конкретную утилиту. Любой элемент, у которого в списке классов встретилось слово `shadow` — включая тех, кто явно просит `shadow-none`, — теряет весь `box-shadow`. А поскольку Tailwind v4 строит `ring-*` тоже на `box-shadow`, вместе с тенью гаснет и кольцо.

Так у `SelectContent` погасли и `shadow-md`, и соседний `ring-1 ring-foreground/10`, а рамки у него не было вовсе. Правило оставлено намеренно: его снятие оживило бы `shadow-*` разом в двух десятках мест. Всплывающие слои выведены из-под него отдельным исключением по `data-slot`.

**Что этим правилом сломано и не чинится сейчас:** drop-индикатор при перетаскивании в настройках (`settings/page.tsx`, `shadow-[0_0_0_3px_var(--card)]`) и подсветка выбранной ноды графа сценариев — `.scenario-graph-node-selected` проигрывает утилите `shadow-sm` на том же элементе.

## Прокрутка

Прокручивается страница целиком: собственного скролла у выдачи нет. Место под полосу зарезервировано всегда — `html { overflow-y: scroll }` в `index.css`.

Именно `overflow-y: scroll`, а не напрашивающийся `scrollbar-gutter: stable`. Замер: у корня гаттер места не резервирует ни сам по себе, ни в паре с `overflow-y: auto` — `documentElement.clientWidth` в обоих случаях гулял между 1189 и 1204. Ноль разницы даёт только `overflow-y: scroll`, ценой всегда видимой дорожки полосы.

Без этого резерва фильтрация двигала весь интерфейс: список укорачивался, документ переставал переполняться, полоса исчезала, и 15px возвращались в колонку контента.

Исключение одно — страница сценариев. Там высота ровно в экран, документ не прокручивается, и зарезервированная дорожка вставала рядом с полосой внутреннего скроллера. Для неё `overflow-y: hidden` объявлен в `react_scenario_workspace_v2.html`.

## Правило про подтверждения

Дополняет запрет `window.confirm` из основного контракта.

**Клиент не подставляет за пользователя флаг осознанного согласия.** Если сервер требует подтверждения массового действия, этот флаг ставится по факту действия человека. Захардкоженный `confirmed: true` в обработчике отключает серверную защиту, оставляя её видимость.

## Ловушка при проверке сборки

Вывод о дрейфе generated output делается по `git diff`, а не по `git status`.

При `core.autocrlf=true` статус держит файлы в `app/static/workspace_v2` «изменёнными» постоянно, хотя содержимое совпадает побайтово. `git status` здесь не является источником правды.
